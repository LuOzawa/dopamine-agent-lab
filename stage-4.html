4.1

六种 Agent 架构：复杂度要花在刀刃上

约 35 分钟 架构 对照原文 ↗

学习目标

根据任务形态选择架构，并能反驳「多 Agent 一定更强」这个假设。

前置知识

阶段 1 的循环；3.1 的推理模式。

核心要点

  • 单 Agent 循环：最常用，适合 80% 的工具型任务；瓶颈是上下文增长。
  • 路由 / 分诊：先判断任务类型，再交给专门的处理链；适合客服、工单等类别清晰的场景。
  • Plan-and-Execute：规划者 + 执行者，适合长任务；需要重规划机制。
  • 多 Agent / 层级：任务可分解且子任务异构时才有收益；协调成本与错误放大是主要代价。
  • 评估器-优化器：生成 + 评审循环，适合有明确质量标准的内容任务；没有外部标准时会退化为互相吹捧。

动手任务（30 分钟）

为「每周自动生成团队周报」和「跨三个仓库的代码迁移」各选一个架构，画不超过 5 个框的图，并写一句「为什么不用更简单的单 Agent」。如果写不出来，说明你不需要更复杂的架构。

自检

什么情况下多 Agent 反而是负优化？
任务线性、上下文可以共享、子任务同质时。多 Agent 会引入信息丢失、重复工作和调试困难，成本上升但质量未必提升。先尝试单 Agent + 更好的工具与提示。
评估器-优化器架构什么时候有效？
当「好」可以被外部标准检验时（测试通过、格式校验、事实核对）。如果只让模型自评，容易产生偏好偏差，评审轮次越多不代表质量越高。

4.2

第一个 Agent 与平台选型：三条轴，不追新

约 30 分钟 选型 对照原文 ↗

学习目标

用「搭建速度 / 系统衔接 / 可控深度」三条轴给候选平台打分，并识别数据锁定与合规风险。

前置知识

3.4 上下文工程；对至少一个平台有初步印象。

核心要点

  • 平台（Dify / n8n / 各类办公 Agent）、框架（LangChain / CrewAI）、库（SDK）解决的是不同层的问题。
  • 先问「一周内能不能验证价值」，再问「以后能不能迁走」。不能导出数据与流程的平台要谨慎。
  • 桌面 Agent 权限大、体验好，但数据边界与误操作风险也更大；优先在独立工作区试用。
  • 产品宣传里的「免费」「支持某模型」变化很快，以官网与合同为准，不要把教程里的价格/额度当事实。
  • 选型输出应该是一页纸：场景、候选、评分、试点计划、退出策略。

动手任务（30 分钟）

列 4 个候选（至少包含 1 个可视化平台、1 个代码框架），按速度 / 衔接 / 可控 / 成本 / 锁定风险打 1–5 分，加权求和。选一个本周做 30 分钟试点，并写下「什么结果会让你放弃它」。

自检

为什么建议先平台后框架？
平台能最快验证需求是否真实，避免一上来写几千行代码后发现没人用。但验证通过后，要评估可迁移性，避免被平台能力锁死。
如何降低平台锁定风险？
数据可导出、提示与流程可版本化、核心逻辑不依赖平台私有节点、保留一个可运行的代码版原型。合同层面确认数据使用与删除条款。

选型补充：13 个 Agent 框架与 8 个工具的对比矩阵（定位 / 适合 / 注意），见 框架与工具选型矩阵。

4.3

AI 工作流：确定性优先，自主性按需

约 30 分钟 架构 对照原文 ↗

学习目标

判断一个需求该做成固定工作流、自主 Agent，还是「工作流里嵌 Agent 节点」的混合形态。

前置知识

4.1 架构；3.1 推理模式。

核心要点

  • 工作流的优势是可预测、可测试、成本可控；缺点是遇到未枚举的情况就断。
  • Agent 的优势是处理开放路径；缺点是难测试、成本波动、可能跑偏。
  • 生产里最常见的是混合：外层工作流保证步骤与审批，内层用 Agent 处理「这一步怎么做」。
  • 每个节点都要定义输入/输出契约、超时、重试与失败兜底，否则编排只是把不确定性藏起来。
  • 能写成 if/else 的，不要交给模型决定——确定性逻辑用代码，语义判断才用模型。

动手任务（30 分钟）

把「每天抓竞品价格 → 对比昨日 → 生成日报 → 发邮件」画成 6 步工作流，并在每一步标注：输入、输出、失败怎么办。最后圈出「哪一步值得用 Agent，哪一步必须用代码」。

自检

为什么「能用工作流就别用 Agent」？
因为工作流的行为可枚举，测试、监控、成本估算都更容易；Agent 的每次执行路径可能不同，出错时更难复现。自主性应该花在真正需要判断的地方。
混合形态里，Agent 节点最容易出什么问题？
输出格式不稳定，导致下游节点解析失败。解决方式是给 Agent 明确的 schema、校验与重试，并设置「解析失败就转人工」的兜底路径。
