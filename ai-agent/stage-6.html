学习目标

前置知识

核心要点

  • 包已拆分：langchain-core（抽象）、langchain-openai（模型）、langchain（Agent 入口）。
  • 1.x 的最小写法：create_agent(model, tools)，返回可直接 invoke 的 Agent。
  • 工具用 @tool 装饰，函数签名与 docstring 就是模型看到的 schema 和描述。
  • 消息状态统一为 messages 列表；调试时打印完整消息链，而不是只看最终回答。
  • 旧教程的 initialize_agent / AgentExecutor 已属 legacy，迁移前先查官方迁移指南。

自检

为什么旧教程的 initialize_agent 现在容易跑不通？
它属于 0.x 时代的 API，相关模块在 1.x 中已迁移或移除；模型类也搬到了独立包。这不是你的环境问题，而是版本断层——按当前官方文档重写更省时间。
LCEL 和 Agent 是什么关系？
LCEL 是组合原语（用管道把组件串起来），适合确定性的链；Agent 是「由模型决定下一步」的循环。两者可以嵌套：Agent 内部节点仍可用 LCEL 组合。

"""真实 create_agent + 两个本地工具，无密钥运行两个固定问题。"""
import ast
import operator
from scripted_model import ScriptedModel, call
from langchain.agents import create_agent
from langchain_core.messages import AIMessage, ToolMessage
from langchain_core.tools import tool


@tool
def weather(city: str) -> str:
    """返回北京或上海的固定教学天气，不是实时天气。"""
    data = {'北京': '22°C 晴', '上海': '25°C 多云'}
    return data.get(city, '错误：仅支持北京或上海')


@tool
def calculate(expression: str) -> str:
    """计算只含数字、括号及加减乘除的算式，不执行任意代码。"""
    ops = {ast.Add: operator.add, ast.Sub: operator.sub,
           ast.Mult: operator.mul, ast.Div: operator.truediv}
    def visit(node):
        if isinstance(node, ast.Constant) and type(node.value) in (int, float):
            if abs(node.value) > 1e9:
                raise ValueError('数字过大')
            return node.value
        if isinstance(node, ast.BinOp) and type(node.op) in ops:
            return ops[type(node.op)](visit(node.left), visit(node.right))
        raise ValueError('仅允许数字和加减乘除')
    try:
        if len(expression) > 100:
            raise ValueError('算式过长')
        return str(visit(ast.parse(expression, mode='eval').body))
    except (ValueError, SyntaxError, ZeroDivisionError, OverflowError) as exc:
        return f'错误：{exc}'


def run(city='北京', expression='(2+3)*6'):
    model = ScriptedModel(steps=[call('weather', {'city': city}, 1),
        call('calculate', {'expression': expression}, 2), AIMessage(content='工具执行完成。')])
    agent = create_agent(model=model, tools=[weather, calculate],
                         system_prompt='使用工具核对天气和算式。')
    return agent.invoke({'messages': [{'role': 'user',
        'content': f'{city}天气如何？计算 {expression}。'}]}, {'recursion_limit': 12})


if __name__ == '__main__':
    print('模式：固定模型响应；真实 LangChain 工具循环')
    for city, expr in [('北京', '(2+3)*6'), ('上海', '8/2')]:
        result = run(city, expr)
        print(f'问题：{city}天气；{expr}')
        for m in result['messages']:
            if isinstance(m, ToolMessage):
                print(f'  工具 {m.name}: {m.content}')
        print('  消息类型：' + ' → '.join(m.type for m in result['messages']))

import os

# 教学离线模式不启用云端 tracing。
os.environ['LANGSMITH_TRACING'] = 'false'
os.environ['LANGCHAIN_TRACING_V2'] = 'false'

from langchain_core.language_models.chat_models import BaseChatModel
from langchain_core.messages import AIMessage
from langchain_core.outputs import ChatGeneration, ChatResult


class ScriptedModel(BaseChatModel):
    steps: list[AIMessage]

    @property
    def _llm_type(self):
        return 'teaching-script-no-network'

    def bind_tools(self, tools, **kwargs):
        return self

    def _generate(self, messages, stop=None, run_manager=None, **kwargs):
        index = sum(isinstance(m, AIMessage) for m in messages)
        if index >= len(self.steps):
            raise RuntimeError('固定响应耗尽：检查工具错误或步骤配置')
        return ChatResult(generations=[ChatGeneration(message=self.steps[index])])


def call(name, args, number):
    return AIMessage(content='', tool_calls=[{
        'name': name, 'args': args, 'id': f'call_{number}', 'type': 'tool_call'}])

LangGraph：把循环画成状态图

约 45 分钟 图编排 对照原文 ↗

学习目标

用 StateGraph 实现「检索 → 判断 → 回答 / 重试」，并加上检查点与循环上限。

前置知识

6.1；理解有向图与状态机。

核心要点

  • 三个基本元素：State（共享数据）、Node（函数）、Edge（流转，可条件分支）。
  • 相比 while 循环，图的价值在显式状态、可持久化、可中断恢复、可视化。
  • Checkpointer 让长任务可以断点续跑，也支撑 human-in-the-loop 审批。
  • 循环一定配递归上限 / 退出条件，否则图会转圈。
  • 节点要小且单一职责，状态字段要少；把大对象塞进 State 会让持久化变慢。

动手任务（45 分钟）

画并实现 4 节点图：retrieve → grade → 条件边 → answer 或 retry。加内存 checkpointer，跑两个输入（一个能答、一个证据不足），验证重试不会无限循环。

自检

什么时候该用 LangGraph，而不是一个 while 循环？
需要持久化状态、断点恢复、人工审批、可视化或多分支协作时。简单线性任务用图反而增加理解成本。
Checkpointer 的实际价值是什么？
它保存执行状态，支持中断与审批后恢复；本课的内存后端仅在当前进程有效。跨进程或崩溃恢复需要持久化后端。

可运行实验 · checkpoint 恢复与有界检索

真实 StateGraph 包含 retrieve、grade、retry、answer 四个节点。第一次检索故意为空，第二次根据固定规则命中或拒答；这验证分支与预算，不模拟语义检索。InMemorySaver 暂停在 answer 前，以同一 thread_id 恢复。

  • 缺少 thread_id：每次 invoke/get_state 都传 configurable.thread_id。
  • 恢复后没有结果：恢复用 graph.invoke(None, 原 config)，不要重新传 initial 状态覆盖本次流程。
  • GraphRecursionError：检查 grade 是否在 attempts >= 2 时路由 answer；示例 recursion_limit 为 16。

"""真实 StateGraph：有界重试、拒答、checkpoint 暂停后恢复。"""
from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver


class State(TypedDict):
    question: str
    attempts: int
    docs: list[str]
    sufficient: bool
    answer: str


def build_graph(pause=False):
    def retrieve(s):
        # 第一次故意未命中，用于确定性验证 retry 分支。
        n = s['attempts'] + 1
        docs = ['密钥放在 .env，不提交到版本库。'] if n == 2 and '密钥' in s['question'] else []
        return {'attempts': n, 'docs': docs}
    def grade(s):
        return {'sufficient': bool(s['docs'])}
    def retry(s):
        return {'answer': ''}
    def answer(s):
        return {'answer': s['docs'][0] if s['sufficient'] else '资料不足，停止检索。'}
    graph = StateGraph(State)
    for name, fn in [('retrieve', retrieve), ('grade', grade), ('retry', retry), ('answer', answer)]:
        graph.add_node(name, fn)
    graph.add_edge(START, 'retrieve')
    graph.add_edge('retrieve', 'grade')
    graph.add_conditional_edges('grade', lambda s:
        'answer' if s['sufficient'] or s['attempts'] >= 2 else 'retry')
    graph.add_edge('retry', 'retrieve')
    graph.add_edge('answer', END)
    return graph.compile(checkpointer=InMemorySaver(), interrupt_before=['answer'] if pause else [])


def initial(question):
    return {'question': question, 'attempts': 0, 'docs': [], 'sufficient': False, 'answer': ''}


def demo():
    graph = build_graph(pause=True)
    for i, question in enumerate(['密钥放哪里？', '火星天气如何？']):
        config = {'configurable': {'thread_id': f'lesson-{i}'}, 'recursion_limit': 16}
        graph.invoke(initial(question), config)
        saved = graph.get_state(config)
        print(f'暂停：next={saved.next[0]}；检索={saved.values["attempts"]} 次')
        result = graph.invoke(None, config)
        print(f'恢复：{result["answer"]}')
    print('存储：进程内 InMemorySaver；退出进程后不保留')


if __name__ == '__main__':
    demo()

CrewAI：角色分工不是越多越好

约 35 分钟 多角色 对照原文 ↗

学习目标

用 3 个角色（调研 / 写作 / 审校）完成一条内容流水线，并解释每个角色的边界。

前置知识

4.1 多 Agent 架构；5.2 工具调用。

核心要点

  • 三要素：Agent（角色 / 目标 / 背景）、Task（描述 / 期望输出）、Crew（流程）。
  • 顺序流程适合有依赖的流水线；层级流程适合需要动态分配的任务，但成本更高。
  • 角色边界要写清「不做什么」，否则会出现重复劳动或互相改稿。
  • 输出用结构化 schema（如 Pydantic）比自然语言「请输出 JSON」可靠。
  • 角色增加会带来额外模型调用与上下文成本；先用 3 个角色测量，不预设成本线性增长。

动手任务（35 分钟）

自检

角色越多效果越好吗？
不是。角色增加会带来协调成本、信息丢失和风格冲突；只有在子任务确实异构、且每个角色都有明确验收标准时才有收益。
如何保证多角色输出格式一致？
给每个任务定义结构化输出模型，并在 Crew 层做校验；不要让下游角色「从自然语言里猜」上游给了什么。

class RoleModel(BaseLLM):
    def __init__(self, output):
        super().__init__(model='offline-script', temperature=0)
        self.output = output
        self.calls = 0
        self.seen = []
        self.task_seconds = 0.0

    def call(self, messages, tools=None, callbacks=None, available_functions=None, **kwargs):
        self.calls += 1
        self.seen.append(str(messages))
        return 'Final Answer: ' + self.output

    def supports_function_calling(self):
        return False

学习目标

核心要点

  • 把「待办清单」外置成文件，模型不必把全部计划塞在上下文里。
  • 文件系统既是工作区也是外部记忆：中间结果落盘，按需读取。
  • 子 Agent 用来隔离上下文：把一个大搜索交给子 Agent，只把结论带回主线程。
  • 上下文压缩、长任务执行、人工审批是「开箱能力」，但仍需你定义验收与权限。

自检

为什么用文件而不是把所有内容留在上下文？
上下文有成本与注意力上限；文件可以持久化、可检索、可人工检查，也方便断点续跑。代价是要设计目录结构与读写规则。
这类框架最大的隐藏成本是什么？
行为不透明：多层抽象后，出错时很难判断是提示、工具、压缩还是子 Agent 的问题。选型时要确认可观测性与可替换性。

"""Dify Chatflow API v1 客户端。默认回放契约样本，--live 才发送网络请求。"""
import argparse
import json
import os
from pathlib import Path
from urllib.request import Request, urlopen
from urllib.error import HTTPError, URLError
from urllib.parse import urlparse


def ask(query, base_url, key, opener=urlopen):
    parsed = urlparse(base_url)
    if parsed.scheme not in ('https', 'http') or not parsed.hostname:
        raise ValueError('DIFY_BASE_URL 必须是完整 http(s) URL，含 /v1')
    if parsed.scheme == 'http' and parsed.hostname not in ('localhost', '127.0.0.1', '::1'):
        raise ValueError('远程服务请使用 HTTPS')
    if not key.strip():
        raise ValueError('缺少 DIFY_API_KEY：使用已发布 Chatflow 的应用密钥')
    payload = {'inputs': {}, 'query': query, 'response_mode': 'blocking', 'user': 'stage6-learner'}
    request = Request(base_url.rstrip('/') + '/chat-messages',
                      data=json.dumps(payload).encode(),
                      headers={'Authorization': 'Bearer ' + key, 'Content-Type': 'application/json'})
    try:
        with opener(request, timeout=30) as response:
            data = json.load(response)
    except HTTPError as exc:
        raise RuntimeError(f'Dify HTTP {exc.code}：检查应用发布、密钥、模型与额度') from None
    except (URLError, TimeoutError):
        raise RuntimeError('Dify 连接失败或超时：检查地址与网络') from None
    except (ValueError, UnicodeError):
        raise RuntimeError('Dify 返回的不是有效 JSON') from None
    return summarize(data)


def summarize(data):
    if not isinstance(data, dict) or not isinstance(data.get('answer'), str) or not data['answer'].strip():
        raise ValueError('响应缺少非空 answer；确认应用类型为 Chatflow')
    metadata = data.get('metadata') or {}
    if not isinstance(metadata, dict):
        raise ValueError('响应 metadata 必须是对象')
    resources = metadata.get('retriever_resources') or []
    if not isinstance(resources, list):
        raise ValueError('retriever_resources 必须是列表')
    names = sorted({r['document_name'] for r in resources if isinstance(r, dict) and r.get('document_name')})
    return {'answer': data['answer'], 'sources': names}


def demo():
    cases = json.loads((Path(__file__).parent/'data/dify-cases.json').read_text())
    print('模式：API 契约样本回放；尚未连接 Dify 知识库')
    for case in cases:
        result = summarize(case['response'])
        print('问题：' + case['query'])
        print('回答：' + result['answer'])
        print('来源：' + ('、'.join(result['sources']) or '无（资料外拒答）'))


if __name__ == '__main__':
    parser = argparse.ArgumentParser()
    parser.add_argument('--live', action='store_true')
    parser.add_argument('--query', default='进度如何保存，换设备后还能继续吗？')
    args = parser.parse_args()
    try:
        if args.live:
            print(json.dumps(ask(args.query, os.getenv('DIFY_BASE_URL', 'https://api.dify.ai/v1'),
                                 os.getenv('DIFY_API_KEY', '')), ensure_ascii=False, indent=2))
        else:
            demo()
    except (ValueError, RuntimeError) as exc:
        parser.exit(1, str(exc) + '\n')

n8n：系统之间的事，交给自动化

约 30 分钟 自动化 对照原文 ↗

学习目标

用 n8n 做一个「请求提交 → 模型处理 → 格式验证 → 回应」自动化，并处理格式失败。

前置知识

4.3 工作流；基本 HTTP 概念。

核心要点

  • 三要素：触发器（Webhook / 定时 / 应用事件）、节点、凭证。
  • n8n 的强项是系统集成与确定性流程，不是复杂推理编排。
  • 每个节点都要考虑幂等：重复触发不能重复发邮件/重复扣款。
  • 错误工作流（Error Workflow）与重试策略要提前配，否则失败无人知晓。
  • 自托管要关注版本升级、数据库备份与凭证加密。

动手任务（30 分钟）

搭建 Webhook → 模型 HTTP 请求 → Code 格式验证 → IF 分支 → 回应。故意让模型返回非 JSON 或缺少字段，检查友好兜底；先用随包的固定输入工作流验证相同分支。

自检

n8n 适合做什么，不适合做什么？
适合定时任务、表单到系统的数据流、跨应用通知；不适合需要复杂状态机、多轮推理或精细上下文控制的任务——那类更适合代码框架。
为什么幂等性在自动化里特别重要？
网络抖动、重试、重复触发都很常见。没有幂等键，一次失败重试可能变成两次发信、两次扣款。用业务 ID 去重是最简单的防线。

可运行实验 · 真实 n8n 引擎的 JSON 兜底

在 n8n 2.44.7 的断网临时容器里执行 Manual Trigger → 固定模型输出 → Validate → IF → 成功或兜底。包含合法 JSON、损坏 JSON、缺字段三条输入。另附可导入的 Webhook → 模型 HTTP 请求 → 同一验证逻辑 → 回应工作流。

"""在断网的临时 n8n 容器中实际执行工作流，并检查成功/失败路由。"""
import json
from pathlib import Path
import subprocess
import uuid

IMAGE = 'docker.n8n.io/n8nio/n8n:2.44.7'
ROOT = Path(__file__).resolve().parent


def parse_execution(output):
    # n8n --rawOutput 前仍可能打印迁移与 runner 日志。
    decoder = json.JSONDecoder()
    for i, char in enumerate(output):
        if char != '{':
            continue
        try:
            value, _ = decoder.raw_decode(output[i:])
        except ValueError:
            continue
        if isinstance(value, dict) and 'data' in value and 'finished' in value:
            return value
    raise RuntimeError('没有找到 n8n 执行结果；检查容器日志')


def verify(result):
    if result.get('status') != 'success':
        raise RuntimeError('工作流失败：' + str(result.get('status')))
    runs = result['data']['resultData']['runData']
    items = [item['json'] for name in ('Success', 'Fallback')
             for run in runs.get(name, []) for branch in run['data']['main'] for item in branch]
    routes = {i['case']: i['route'] for i in items}
    if routes != {'valid': 'success', 'malformed': 'fallback', 'missing-field': 'fallback'}:
        raise RuntimeError('分支结果与验收不符：' + str(routes))
    return items


def main():
    name = 'stage6-test-' + uuid.uuid4().hex[:12]
    cmd = ['docker', 'run', '--rm', '--name', name, '--network', 'none',
           '-e', 'N8N_DIAGNOSTICS_ENABLED=false', '-e', 'N8N_VERSION_NOTIFICATIONS_ENABLED=false',
           '-e', 'N8N_TEMPLATES_ENABLED=false', '-e', 'N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true',
           '-v', f'{ROOT / "n8n"}:/work:ro', '--entrypoint', '/bin/sh', IMAGE, '-c',
           'n8n import:workflow --input=/work/offline.json >/tmp/import.log && '
           'n8n execute --id=Stage6Smoke --rawOutput']
    try:
        result = subprocess.run(cmd, text=True, capture_output=True, timeout=120)
    finally:
        # 超时杀掉 Docker CLI 后也清理本次容器；不会操作其他容器。
        subprocess.run(['docker', 'rm', '-f', name], capture_output=True, timeout=15)
    if result.returncode:
        raise RuntimeError('n8n 执行失败：\n' + (result.stderr + result.stdout)[-2000:])
    items = verify(parse_execution(result.stdout))
    print('n8n 2.44.7：真实工作流；容器断网；模型输出为固定样本')
    for item in items:
        print(f'{item["case"]} → {item["route"]}：{item["summary"]}')
    print('3/3 分支验收通过；容器退出即删除数据库')


if __name__ == '__main__':
    try:
        main()
    except (RuntimeError, FileNotFoundError, subprocess.TimeoutExpired) as exc:
        raise SystemExit(str(exc))

`n8n/offline.json` 在真实 n8n 引擎中执行 Manual Trigger → Fixture → Validate → IF → Success/Fallback。三条样本为合法 JSON、损坏 JSON、缺少 summary。Validate 不会因 JSON.parse 报错终止整个任务，IF 选择友好兜底。容器没有网络，资料只读挂载，数据库不持久化，不发送通知。

## Webhook 与真实模型

`n8n/webhook.json` 是可导入的在线版本：Webhook → Model（HTTP Request）→ Validate → IF → Reply。Validate/IF 与离线版本完全相同。在线版已做结构检查，尚未在已发布 webhook 上端到端验证。

1. 在 n8n 2.44.7 的编辑器 Import from File，导入 webhook.json。
2. Model 节点选择 Header Auth 凭据；Header 名为 `Authorization`，值为 `Bearer 你的模型密钥`。凭据保存在 n8n 凭据管理器，不写进 JSON。模型默认 `gpt-5.4-mini-2026-03-17`，可换为账号有权限且支持 Responses 的模型。
3. 点击 Webhook 的 Listen for test event。复制节点显示的 Test URL（仅测试监听期间有效），以 JSON 发送 `{"text":"学习站提供分阶段课程和本地进度。"}`。
```sh
curl -X POST 'http://localhost:5678/webhook-test/stage6-summary' \
  -H 'Content-Type: application/json' \
  -d '{"text":"学习站提供分阶段课程和本地进度。"}'
```
4. 正常应返回 `ok:true`、非空 summary、`route:"success"`；Model 节点请求失败、非 JSON 或缺字段时返回 `ok:false`、友好提示及 `route:"fallback"`。响应措辞不固定。检查执行记录确认失败发生的位置。
5. 需要长期使用才发布，并使用 Production URL；对外暴露前给 Webhook 配置认证。示例只回应请求，不接通知服务。

默认最多一次模型 HTTP 请求，30 秒超时，256 输出 tokens；这不是费用上限。在线模式会把输入发给模型服务。当前 prompt 要求 JSON 但不保证模型遵守，所以仍保留验证与兜底。

## 常见报错

- Docker daemon 无法连接：启动 Docker Desktop；确认当前用户可访问 Docker。
- Mounts denied：允许 Docker 访问解压目录；完整解压，不要只复制启动器。
- 镜像不存在：先 pull 固定版本；离线容器不负责下载模型。
- 120 秒超时：检查 Docker 资源和启动日志；不要把超时改成无限。
- 401：Model 节点没有绑定 Header Auth 或密钥无效。工作流仍应进入 fallback。
- Webhook 404：测试 URL 需要监听；生产 URL 需要发布。
- 编辑器节点类型不支持：确认 n8n 2.44.7，旧版本不在本次验证范围。

判断一个需求该用向量 RAG 还是 GraphRAG，并估算索引成本。

前置知识

3.3 RAG；基本的图/实体关系概念。

核心要点

  • GraphRAG 先用模型抽取实体与关系，建图并生成社区摘要，再基于图做检索。
  • 优势在「全局性问题」：跨文档总结主题、发现实体间的间接联系。
  • 成本在索引：抽取与摘要要跑很多次模型调用，更新文档需要增量重建。
  • 小数据、低延迟、频繁更新、强精确匹配的场景，向量 RAG 更划算。
  • 它不替代原文：答案仍要回到源文档核对，图只是索引结构。

动手任务（30 分钟）

选 5 篇同主题文章，提 2 个「全局问题」（如「这批文档反复提到的三个风险是什么」）和 2 个「局部问题」。先判断哪些问题向量 RAG 也能答，再决定是否值得跑一次 GraphRAG 索引。

自检

GraphRAG 最大的成本在哪里？
索引阶段：实体/关系抽取与社区摘要需要大量模型调用，且文档更新后要维护增量索引。查询阶段相对便宜，但图质量决定上限。
什么时候不该用 GraphRAG？
数据量小、问题以事实查询为主、要求低延迟或文档每天变化时。此时向量检索 + 重排通常足够，维护成本更低。

常见报错与处理

  • 目标已存在：prepare 拒绝覆盖已有项目；指定新目录或继续使用原项目。
  • 旧版 models 配置报错：3.3.0 使用 completion_models / embedding_models；用本版本 init 生成。
  • 缺少实体/社区报告文件：先完成真实 index；dry-run 不生成这些文件。
  • 401 / 404 / 429：核对密钥、模型权限与额度；离线检查无法验证这些。

"""实际 GraphRAG CLI 初始化/配置检查。默认不建索引、不调用模型。"""
import argparse
import os
from pathlib import Path
import shutil
import subprocess
import sys
import tempfile

ROOT = Path(__file__).resolve().parent


def prepare(path):
    if path.exists():
        raise ValueError('目标已存在：请指定新目录，避免覆盖已有配置和密钥')
    path.mkdir(parents=True)
    cli = Path(sys.executable).with_name('graphrag.exe' if os.name == 'nt' else 'graphrag')
    env = dict(os.environ, LITELLM_LOCAL_MODEL_COST_MAP='True', GRAPHRAG_API_KEY='offline-placeholder')
    commands = [[str(cli), 'init', '--root', str(path), '--model', 'gpt-5.4-mini-2026-03-17',
                 '--embedding', 'text-embedding-3-small'],
                [str(cli), 'index', '--root', str(path), '--dry-run', '--skip-validation']]
    for i, cmd in enumerate(commands):
        proc = subprocess.run(cmd, env=env, capture_output=True, text=True, timeout=90)
        if proc.returncode:
            raise RuntimeError('GraphRAG CLI 失败：\n' + (proc.stderr + proc.stdout)[-2000:])
        if i == 0:
            shutil.copytree(ROOT/'data/articles', path/'input', dirs_exist_ok=True)
    if not (path/'settings.yaml').is_file() or len(list((path/'input').glob('*.txt'))) != 5:
        raise RuntimeError('项目材料不完整')
    print('GraphRAG 3.3.0：init 完成；5 篇教学资料已复制')
    print('index --dry-run --skip-validation：配置检查通过')
    print('模型请求=0；未生成实体、社区报告或向量索引')


if __name__ == '__main__':
    parser = argparse.ArgumentParser()
    parser.add_argument('--prepare', type=Path, help='保留项目供真实 API 实验，目标必须不存在')
    args = parser.parse_args()
    try:
        if args.prepare:
            prepare(args.prepare.resolve())
            print('下一步：按 GRAPHRAG.md 配置密钥，再真实 index/query。')
        else:
            with tempfile.TemporaryDirectory(prefix='stage6-graphrag-') as tmp:
                prepare(Path(tmp)/'project')
            print('临时项目已清理；真实检索质量与费用尚未测量')
    except (ValueError, RuntimeError, FileNotFoundError, subprocess.TimeoutExpired) as exc:
        parser.exit(1, str(exc) + '\n')

# 6.7 GraphRAG 3.3.0

使用 Python 3.11 独立环境，依赖见 requirements/graph-lock.txt。5 篇中文教学短文在 data/articles/；短文足以练习流程，但不是验证 GraphRAG 优势的基准数据。

## 无密钥检查（已实跑）
```sh
python s67_graphrag.py
```
真正调用官方 CLI 的 init 和 index --dry-run --skip-validation。临时项目随后清理。skip-validation 跳过模型连接检查，dry-run 不建索引；成功仅代表配置通过，不代表 API 可用。脚本给子进程注入离线占位值，不读取或覆盖你的模型密钥。LiteLLM 使用随包价格表，避免启动时联网获取价格。

## 建立真实索引（需密钥，未在线实测）
```sh
python s67_graphrag.py --prepare .runtime/graphrag
```
已有目录时脚本拒绝覆盖。用编辑器打开新项目的 `.runtime/graphrag/.env`，把生成的 `GRAPHRAG_API_KEY` 填为自己的密钥；不要上传该文件。检查 settings.yaml 的 completion_models 与 embedding_models：默认模型分别为 gpt-5.4-mini-2026-03-17 和 text-embedding-3-small，账号必须有权限。再执行：
```sh
graphrag index --root .runtime/graphrag
graphrag query --root .runtime/graphrag --method global --query "这些材料共同关注哪些目标和风险？"
graphrag query --root .runtime/graphrag --method global --query "团队如何分工保障发布质量？"
graphrag query --root .runtime/graphrag --method local --query "李明负责什么，并与谁协作？"
graphrag query --root .runtime/graphrag --method local --query "导航学习站的进度能跨设备同步吗？"
```
命令需在 `.venv-graph` 环境内执行，或将 graphrag 换为该环境的完整路径。索引会对资料调用模型和 embedding，耗时与费用取决于模型、重试、分块和提取设置。先用这 5 篇小材料观察日志；本例没有预设美元费用，也没有宣称真实建索引已通过。

## 同数据、同问题比较普通 RAG

完成同一索引后，对上述四问分别改用 `--method basic`，这是官方提供的基础向量检索查询，可保持相同语料与 embedding，避免拿不同资料比较。
```sh
graphrag query --root .runtime/graphrag --method basic --query "团队如何分工保障发布质量？"
```
注意：basic 在已建好的 GraphRAG 项目上查询；本次总索引费用包含图提取，不能当作普通 RAG 独立索引成本。要比较完整系统成本，需另测只做分块与 embedding 的基线。

预期事实（不是承诺的模型原文）：

| 问题 | 应覆盖的证据 | 验收 |
| --- | --- | --- |
| 共同目标与风险 | 01 降低入门成本；02 可复现性；04 失败覆盖；05 费用与生产监测 | 全局问题应整合多篇，不只复述第一篇 |
| 分工保障质量 | 01、04、05：李明课程、王悦平台、陈晨评审、交叉核对 | 关系不混淆，可定位来源 |
| 李明的职责 | 02、04、05：课程、修复代码、与陈晨核对 | 局部实体相关事实完整 |
| 跨设备进度 | 03：仅当前浏览器、不自动同步 | 不因图检索补出不存在的云端功能 |

逐问记录方法、答案、引用、漏项、耗时、请求数和实际 token 用量；区分索引一次性成本与每次查询成本，费用按服务账单核对。GraphRAG 在这个小数据集上不一定更好，不预填任何质量或费用结论。

常见报错：

- `No module named graphrag` / CLI 找不到：使用 .venv-graph 及对应锁定依赖。
- 配置缺少 completion_models：不要沿用 2.x 的 models 配置；用本版本 init 生成。
- 找不到 input：运行 prepare 后确认有 5 个 .txt；单独 init 不会自动提供资料。
- 401/404/429：分别核对密钥、模型权限/名称、额度与速率；dry-run 不会发现这些问题。
- 缺少 entities / communities / community_reports 等表：先确认真实 index 成功，dry-run 不产生这些文件。
- 没有提取出实体：检查输入、extract_graph 的 entity_types 与语言提示，查看 logs，不能以空图结果下质量结论。
