框架与工具选型矩阵

把原文首页提到的 13 个 Agent 框架和 8 个工具/平台放到一张表里：定位、适合谁、注意什么、本站先看哪一节。 定位来自原教程，评价是学习建议，不是 benchmark。

使用前提：版本、许可证、价格与可用地区变化很快。表里的「适合 / 注意」用于缩小候选，不构成选型结论； 真正决定前，跑一个 1 天能完成的最小 demo，并核对官方文档。

01先问三个问题

① 流程确定吗？

步骤可枚举 → 用工作流（4.3）；路径不确定 → 用 Agent。大多数“Agent 需求”其实是工作流。

② 团队是什么栈？

Python → LangGraph / LangChain / CrewAI / PydanticAI；TypeScript → Mastra；.NET → Semantic Kernel。

③ 能接受多大锁定？

平台快，但要看数据/流程能否导出；库灵活，但状态、部署、观测要自己搭。

04怎么用这张表

推荐路径：先定形态，再选工具，最后写代码
步骤做什么对应小节
1 · 定形态先判断是工作流、单 Agent 还是多 Agent；写不出一页纸的流程就别选框架4.1 架构 · 4.3 工作流
2 · 选平台需要可视化/快速验证 → Dify、n8n；需要代码控制 → LangChain / LangGraph4.2 平台选型
3 · 搭最小闭环手写一次循环 + 2 个工具，再决定用哪个框架替代样板代码5.4 Python 实现 Agent
4 · 上多 Agent只有子任务异构、且单 Agent 已验证不够时，才引入 CrewAI / AutoGen / Swarms8.1 多智能体
5 · 控长期运行长任务用图/检查点；持续改进用 harness 与 loop 的预算、验证、停止条件6.2 LangGraph · 7.2 · 7.3

一个反直觉建议：先用「模型 + 3 个工具 + 一个循环」跑通需求，再选框架。框架解决的是协作、状态与运维， 不是需求验证；先选框架再找问题，通常会把复杂度花在不需要的地方。
